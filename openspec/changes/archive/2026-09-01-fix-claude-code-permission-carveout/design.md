## Context

See `proposal.md` - Why for the defect. Facts that shape the approach, verified against Claude Code's published docs (code.claude.com/docs/en/permissions, /docs/en/hooks) at proposal time:

- Permission rules are evaluated deny, then ask, then allow, first match wins, "rule specificity doesn't change the order." Deny cannot carry an allow exception. There is no negation in the gitignore-style pattern syntax. So "deny the store root except the worktree" is not expressible as permission rules at all, in any arrangement of deny/ask/allow.
- Claude Code consults `Edit(path)` and `Read(path)` rules only; a `Write(path)` rule is accepted but never checked.
- A PreToolUse hook receives the tool call's JSON envelope on stdin (`tool_name`, `tool_input.file_path` for Edit/Write/NotebookEdit, `cwd`) and can return a structured allow/deny/ask decision on stdout, independently of the static permission rules. This is the one mechanism that can express "outside X but not Y" as ordinary path logic instead of pattern matching.
- `<store root>/.claude/settings.json` is generated by `ctxr adapters generate` / `ctxr update` only — `ctxr init` never calls the generator, and the file is neither committed nor gitignored. `test/integration/adapters-and-entry-doc.test.ts` asserts it is absent in a freshly started session worktree. So whatever this change ships only ever takes effect for a Claude Code session whose project directory is the store root itself.
- `mergeJsonArrayLists` (`src/core/json-config-merge.ts`) is an append-only union over `Record<string, Record<string, readonly string[]>>` sections. It has no removal path and cannot merge an array of objects (`hooks.PreToolUse`) at all today.
- The repo already has one hook-shipping pipeline, for git hooks: `templates/hooks/*.sh` rendered with `__CONTEXTURE_BIN__` substitution, written idempotently, chmod'd executable (`src/core/hooks.ts`).
- `src/core/write-lifecycle/path-gate.ts`'s `sanctionedPath` is, by its own header comment, meant to be the store's one path gate so the pre-commit allowlist and any other path check can never disagree.

## Goals / Non-Goals

**Goals:**
- Make the generated Claude Code config actually deny writes to the canonical checkout's own content while leaving the active session worktree writable — the originally intended behavior.
- Repair already-generated `.claude/settings.json` files, not just future ones.
- Reuse the existing path-gate and hook-shipping machinery rather than building parallel mechanisms.

**Non-Goals:**
- Extending protection to sessions opened directly inside a worktree (see proposal.md - Non-goals).
- Covering Bash output-redirect writes (see proposal.md - Non-goals).
- A general-purpose object-array JSON merge library; the merge extension here is scoped to what `hooks.PreToolUse` needs.

## Decisions

### Enforcement primitive: PreToolUse hook, not permission rules

Considered and rejected:
- **Narrower anchored deny rules** (e.g. `Edit(//<root>/<each-content-path>/**)` instead of `Edit(//<root>/**)`, with no allow carve-out needed because anchored patterns don't reach into the worktree). This is expressible in pure permission-rule syntax and needs no new mechanism. Rejected because its coverage depends on enumerating every content path from config and re-enumerating whenever a new one is added — a directory nobody thought to list stays silently unprotected, which is the same class of silent gap the current bug already represents. A hook evaluates the actual resolved path at call time, so it has no such enumeration gap and needs no maintenance when the store's directory layout changes.
- **Ask instead of deny** for the broad rule: does not help — ask beats allow by the same ordering rule that makes deny beat allow.
- **Delete the broken rules and rely on the working-directory boundary**: the working directory *is* the store root for the only sessions this file ever governs, so there is no boundary to rely on. Rejected as leaving the original requirement unmet.

### Retired-rules declaration, exact-match removal only

The generator declares the exact legacy strings it used to emit (reconstructable from `{root, worktreesPath}` alone, mirroring the existing `RETIRED_AGENTS_MD_IDENTITY_FENCE` / `removeFencedRegionFromFile` pattern in `src/core/reconcile.ts`). The merge writer removes exact matches before unioning in the current rules.

Rejected alternative: a predicate sweep (e.g. "remove any `Edit(//<root>/**)`-shaped rule"). This would also catch a rule an operator added by hand with the same shape, which breaks the merge writer's documented and tested guarantee that a hand-added rule survives regeneration untouched (`test/unit/json-config-merge.test.ts`). Exact-match removal cannot over-reach in this way.

Known limitation: if `session.worktrees_path` changed between the store's original generation and the fix landing, the reconstructed legacy strings won't match what's on disk and the stale `allow` entries linger. They are inert (no rule can rely on them; they no longer overlap anything protected), so this is accepted rather than solved with a broader sweep that would reintroduce the hand-added-rule risk above.

### `hooks.PreToolUse` merge: match by command path, not full object equality

`mergeJsonArrayLists`'s string-array union can't merge object arrays. The extension identifies contexture's own hook entry by its `command` field (the path to the generated script) and replaces that entry in place on each run, leaving any other entry in the array (an operator's own hook) untouched. This keeps the same idempotence property the string-array path already has: a second `generate` run produces byte-identical output.

### `permissionConfig.render`'s input, widened

Today's input is `{ root, worktreesPath }`. Installing a hook script needs the CLI's own resolved bin path (already available via `resolveOwnBinPath()` in `src/core/hooks.ts`) and a place for the adapter to declare which template to install and where. The render input widens to carry these; the adapter interface (`src/adapters/types.ts`) gains a way to declare an installable hook file alongside `render()`, analogous to how git hooks are declared. This does not require a `harness-generation` interface-version bump: `permissionConfig` is optional, and only this repo's built-in adapters implement it today, so no external adapter's contract is broken by widening its shape.

### New subcommand for the gate logic: `ctxr adapters write-gate`

Grouped under the existing `adapters` command family (alongside `adapters generate`) rather than a new top-level command, since it is generation's runtime counterpart — one produces the hook wiring, the other is what the wiring invokes. It reads the PreToolUse JSON envelope on stdin and reuses `sanctionedPath` plus a new worktree-scope predicate; it does not reimplement path resolution.

The hook script itself (`templates/hooks/claude-code-write-gate.sh`) stays a thin, dumb shim — mirroring `templates/hooks/pre-commit.sh`'s shape (missing-binary guard, then delegate) — so all judgment is in the CLI where it's unit-testable, and the shipped-prose convention (script text lives in `templates/`, never a TS string literal) is honored.

### Gate exit-code contract

Per the hook contract: exit 2 hard-blocks the tool call regardless of JSON output; other nonzero exit codes are non-blocking errors; exit 0 with a `permissionDecision: "deny"` JSON body blocks with a reason; exit 0 with no output lets the normal permission flow apply. The gate command:
- denies (JSON body, exit 0) when the resolved path is under the store root and outside the active session worktree;
- exits 0 with no output when the path is inside the worktree or outside the store entirely, so normal flow (including any operator-added rules) still applies;
- never emits `permissionDecision: "allow"` — doing so would auto-approve edits an operator's own rules might otherwise gate, silently widening permissions instead of narrowing them;
- on its own errors (unparseable stdin, no resolvable store) exits nonzero but never 2, so a bug in the gate degrades to "normal permission flow applies" rather than "every edit is blocked."

## Risks / Trade-offs

- **A hook is a process spawned per matched tool call.** [Risk: adds latency and a new failure mode to every Edit/Write/NotebookEdit call in root-level sessions] → Mitigation: the gate does trivial path arithmetic (no I/O beyond resolving the store config), and its error contract (above) fails open on its own bugs rather than blocking work.
- **The fix only reaches stores that re-run `adapters generate` or `update`.** [Risk: a store that never regenerates stays broken] → Mitigation: this is the existing regeneration model for every other generated file in the store (`CLAUDE.md`, git hooks); no change introduces a new staleness class beyond what already exists, and `doctor` already has a precedent for detecting stale generated hooks (`detectStaleHooks` in `src/core/hooks.ts`) that a future change could extend to this file — out of scope here.
- **Reduced coverage vs. a full enumeration approach for directories the hook doesn't reach.** Not applicable here — the hook evaluates actual resolved paths, so, unlike the rejected anchored-deny-rules alternative, there is no enumeration gap to trade off.

## Migration Plan

No explicit migration step for operators: the retired-rules removal (see Decisions) runs automatically the next time `ctxr adapters generate` or `ctxr update` executes against an existing store, converging its `.claude/settings.json` to the corrected shape in that one run. Rollback is reverting the contexture version and regenerating again, which re-emits the old (broken) shape; no data migration is involved since the file is derived and untracked.

## Open Questions

None — the enforcement primitive, the retirement mechanism, the merge extension, and the subcommand placement are all decided above.
