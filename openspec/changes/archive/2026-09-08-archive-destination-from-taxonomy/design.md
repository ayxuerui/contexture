## Decisions

**D1 — The profile declares the destination; the archive command still reads one config key.** The alternative — having `ctxr archive` look up the taxonomy and find a layer named "Archives" — was rejected on two grounds. It hardcodes a PARA concept into a command that must work under every profile, and it violates the invariant that `src/taxonomy/profiles.ts` is the only module where a shipped layer name may appear (`test/unit/single-source-literals.test.ts` enforces this). Declaring `archiveDestination` on `TaxonomyProfile` keeps the literal in the one file allowed to hold it and leaves every consumer reading `config.organize.archive_destination`, exactly as before.

**D2 — `archive_destination`, not `archives_path`.** The key names "wherever archived notes land, under any taxonomy," deliberately not "the PARA Archives layer." Naming it after a PARA layer would encode the coupling D1 avoids, and would read wrong under Diataxis, where the value stays `archive/`. The plural also parses as "the destination *of* the Archives layer," which is incoherent — a layer does not have a destination, it is one. The singular `archive` names the act, keeping symmetry with `ctxr archive`, while `_destination` carries the "path moved to" meaning. This matches the schema's existing habit that the key names a concept and the value carries the directory (`inbox_path: inbox/`, `guidance_path: .contexture/guidance/`).

**D3 — Key rename and value adoption are independent, and only the rename is unconditional.** Every schema-5 store gets `archive_destination`; only a store still sitting on the shipped `archive/` default, whose profile declares a destination, gets its value changed. Rewriting an operator's deliberate choice because a default moved would be the migration overstepping. A custom taxonomy resolves to no shipped profile and is left alone for the same reason.

**D4 — `OrganizeSchema` gains a fallback transform rather than a required new key.** Modeled on `HarnessSchema`'s handling of `procedures_path`/`conventions_path`: the old spelling is accepted at load so a schema-5 store still parses and `ctxr migrate` can run, and it is resolved away before `readConfig` returns, so no consumer ever sees it. Following the `guidance_path` precedent rather than the `skills_path` one, an unmigrated store loads silently onto the fallback instead of erroring — this key always had a workable default, so nothing breaks before the migration runs. The transform keeps `mission_path` optional via a conditional spread, so no existing `StoreConfig` literal needs a new key just to compile.

**D5 — Pending-ness is `schema_version < 6`, not key presence.** The rule 0002, 0004, and 0005 established, for the same reason: D4's fallback transform populates `archive_destination` on an unmigrated store too, so its presence cannot distinguish migrated from not.

**D6 — The directory move is skipped when the destination already exists.** Unlike 0004's guidance directory, a store can plausibly hold both `archive/` and `archives/` — the latter being the PARA layer created at init. Renaming onto an existing directory would fail or clobber, so the migration moves only when the destination is absent, and changes the config either way. A store with both keeps its files where they are and gets a correct config, which the operator can reconcile by hand.
