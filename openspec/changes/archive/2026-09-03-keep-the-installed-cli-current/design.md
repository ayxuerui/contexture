## Context

See proposal.md — Why. The constraints that shape the approach, rather than the motivation:

- **`src/` has no outbound network call today.** The only `node:http` import is the local server; the one place that reaches the network is a maintainer-only script that shells out to `gh`, carrying the comment "Network access lives only here — never in src/."
- **That stance is written down as a rejected alternative.** The archived `2026-09-02-keep-external-dependencies-current` change lists "Fetching vendored skills client-side, at `ctxr init` or `ctxr update`" under Non-Goals, with four reasons. This change contradicts the letter of that entry and has to say why (D1).
- **`ctxr session start` already reaches the network.** It fetches the default branch from the remote before creating the worktree. Whatever "offline" means in this codebase, it has never covered that command.
- **The run environment is the one testable seam.** Commands receive an injected environment carrying the io streams, a git runner, a prompter, and a clock; only the real entry point constructs the real implementations. Tests build a fake and get real command behavior with no process-global mutation.
- **Exactly one object may write to stdout**, and it enforces "emitted once" at runtime; a guard test fails any direct stdout write from a command. Its stderr channel (`info`/`warn`/`error`) exists and has no callers yet.
- **`ctxr update` already owns the word "update"** for re-rendering a store's contexture-owned files. It is not, and must not become, a self-updater.
- **Everything the CLI writes lands inside a store root.** Nothing is written to the user's home directory anywhere in the codebase, and the integration tests run with `HOME` pointed at a nonexistent path, so anything written there would vanish silently rather than fail loudly.

## Goals / Non-Goals

**Goals:**

- Introduce network access to `src/` in exactly one place, injectable and faked in tests, so the blast radius is a single port rather than a habit.
- Make the advisory incapable of changing any command's outcome — not merely unlikely to.
- Put the operator's decision in skill markdown, where judgment belongs, and keep the CLI reporting facts.
- Add no runtime dependency and no new user-global state.

**Non-Goals** (design-level; see proposal.md — Non-goals for scope):

- A general-purpose HTTP client, retry policy, or request abstraction. One endpoint, one request, one timeout.
- Reusing the advisory machinery for anything other than the CLI's own release.
- Making the cache correct across concurrent invocations. A duplicated request under a race costs one HTTP call; locking costs more than it saves.

## Decisions

**D1 — The archived rejection of client-side fetching was about delivering third-party prose, and three of its four objections do not transfer to fetching a version number.** `keep-external-dependencies-current`'s Non-Goals entry rejected client-side fetching of vendored skills for four stated reasons; taken one at a time against this change:

1. *"It would put network access in `src/`, which is deliberately network-free."* This one partly transfers, and is the reason the port in D2 exists. But the claim was never literally true of the commands this change touches: `ctxr session start` already fetches from the remote. The advisory adds a second reason for a command that is already online to be online.
2. *"Make `init` non-deterministic and dependent on connectivity, against that command's stated offline guarantee."* Does not transfer — `init` is excluded, and the exclusion is a requirement, not an intention.
3. *"Require HTTP stubbing across the whole `fake-env` test surface."* Does not transfer. That objection assumed intercepting HTTP; an injected port needs one fake alongside the existing git and prompter fakes, and no interception anywhere.
4. *"Decisively, deliver upstream prose to a user's agent as instructions with no human having read it."* Does not transfer at all, and it was the load-bearing reason. A version string is a fact the CLI compares numerically; it is never rendered into a skill, never read as an instruction, and cannot carry a payload.

The same entry's companion rejection — "A store-side staleness check in `ctxr doctor`. `doctor` stays offline, and a store cannot act on the answer anyway" — is *upheld* here, and for both of its reasons. `doctor` stays offline as a requirement, and the asymmetry in the second reason is exactly what justifies this change: a store genuinely cannot act on stale *vendored payload*, because refreshing it is a contexture release, but an operator absolutely can act on a stale *CLI*, because upgrading it is one command they own.

**D2 — Network access enters through one injected port on the run environment, not a module-level `fetch`.** A registry client joins the git runner and the prompter as an injected dependency, constructed only where the real environment is built. Alternatives rejected: importing `fetch` directly in the command (untestable without HTTP interception, and it would make "no network in `src/`" unenforceable by inspection); a module-level singleton with a test override (process-global mutation, which this codebase avoids by construction). The port also means the count of network-capable seams stays greppable at one.

**D3 — The advisory rides `ctxr session start` because that is where the skill path begins and where the network is already in play.** The alternative sites all cost more than they return: every command taxes an inner loop that runs dozens of times a session; `doctor` sits in the commit hook; `init` has an offline guarantee. `session start` runs once per session, already fetches from the remote, is never invoked from a hook, and is the command the lifecycle skill names first — so the operator is present and the session has not yet begun. `ctxr update` is added as the human-path trigger for the same reason a version notice belongs there: it is the command someone runs *after* upgrading, so it is where "you have not upgraded" is most actionable.

**D4 — The advisory is a finding plus a stderr notice, never an exit code.** The envelope's findings array is the structured channel an agent reads, and `info` severity is already the vocabulary for "worth knowing, not a problem." Routing the human notice through the reporter's existing stderr channel preserves the "stdout is exactly one JSON value" contract mechanically rather than by convention. Rejected: raising the check-failed code (would make a stale CLI look like a broken store, and would fail the pre-push hook path for anyone who wires it); printing to stdout (breaks `--json` for every caller).

**D5 — The advisory helper is non-throwing by construction, and this is a requirement rather than an intention.** `session start` creates a git worktree *before* the advisory runs, and the shared command wrapper maps any escaping error to the internal-error code. An unhandled rejection from the registry client would therefore report a failed session that had in fact succeeded, leaving an orphan worktree the operator now has to reason about. Every failure mode — timeout, DNS failure, non-success status, unparseable body, unreadable or unwritable cache — collapses into one informational finding. The helper returns findings; it does not throw, and a test asserts that across the whole failure matrix.

**D6 — The cache is store-local, under the existing derived-cache directory, not user-global.** A user-global cache would be the first thing this codebase ever writes outside a store root, and under the integration tests' hermetic `HOME` it would write to a nonexistent path and silently do nothing — a test surface that passes while testing nothing. The store's derived-cache directory is already inside the managed gitignore fence and already declared in the derived paths, so it needs no new plumbing and never rides review. The cost is a duplicated request per store per interval, which is one HTTP call a day against a CDN. The explicit check sidesteps the question entirely by not caching, which is also what lets it run without a store.

**D7 — Version comparison is hand-rolled over the three-part shape, and refuses anything else.** Every published release is a plain three-part version; there are no prereleases, no build metadata, and no range syntax anywhere in the problem. A comparison that parses exactly that and returns "undeterminable" for anything else is a few lines, adds no dependency, and fails in the correct direction — the fail-loud contract applied to parsing, where the thing that cannot be determined is named rather than guessed past. Rejected: adding a semantic-versioning dependency (a dependency for one numeric comparison, on a project with five runtime dependencies total); string comparison (wrong at the first two-digit minor).

**D8 — The version flag does not go through the argument parser's built-in version support.** The program routes both of the parser's output streams to stderr, deliberately, so that parser chatter can never contaminate `--json` stdout. The built-in version support writes through that same stream, which would put the version on stderr — the one place a version query must not be. The flag is therefore recognized ahead of parsing and dispatched to the same command path as the subcommand, so both produce one envelope on stdout and cannot drift apart.

**D9 — The operator is asked by the agent, in skill markdown, not by the CLI.** On the path this change exists for, `ctxr` is a subprocess with no controlling terminal, and under `--json` the no-input flag is implied — so a prompt from inside the command would be skipped on nearly every invocation that matters, and would appear to work only when a human ran the command by hand. The project's code/judgment seam already assigns this: the CLI computes and verifies, agents read and decide. So the command reports a fact and the skill decides what to do about it. This also keeps the decision reviewable — the skill is markdown an operator can read and edit, not behavior compiled into a binary.

**D10 — Upgrading is a skill that drives the package manager, not a `ctxr upgrade` command.** Three reasons. The upgrade needs consent the CLI cannot obtain (D9). A process that replaces its own running executable mid-invocation is a failure mode not worth owning. And the skill has to make a judgment the CLI should not make alone — a linked working copy must not be told to run a global install — which is exactly the shape of decision that belongs in markdown, informed by a fact the CLI supplies. Driving an external tool from an owned skill is established practice here: submit and land drive `git` and `gh`. The existing check over rendered skills resolves long options only against contexture commands, so a package-manager invocation is outside what it resolves, while `ctxr version --check` inside the same skill *is* checked — which is a benefit: the skill cannot outlive the option it documents.

**D11 — The registry is queried directly over HTTPS rather than by shelling out to the package manager.** Shelling out would honor a user's configured registry and proxy, but costs a subprocess spawn measured in seconds on the session-start path, and inherits the package manager's own failure modes and output format. A direct request to the public registry's per-version endpoint is one small JSON document with a bounded timeout. The trade is stated in the proposal's Non-goals: an operator behind a private mirror gets an honest "could not determine" rather than a wrong answer, and pays nothing for it because the advisory never fails a command.

**D12 — The install-kind classification is computed by the CLI, not sniffed by the skill.** Whether the running executable is a global install or a linked working copy is a fact derivable from the resolved path of the running entry point, which the CLI already resolves for baking into git hooks. Having the skill shell around to work it out would duplicate that logic in markdown, where it cannot be tested. The CLI reports `global`, `linked`, or `undetermined`; the skill branches on it. `undetermined` is a real third answer, not a synonym for `global` — an unrecognized layout stops the skill rather than guessing.

## Risks / Trade-offs

- **The absolute executable path baked into installed git hooks could be invalidated by an upgrade** → The hooks embed an absolute path to the installing executable so they invoke the exact contexture that installed them. A package-manager upgrade is expected to replace the file at that path in place, leaving the path valid — but this is an assumption, and if it is wrong every store on the machine gets hooks pointing at a missing binary, which surfaces as broken commits rather than as a failed upgrade. Verify it explicitly rather than assume it; if it does not hold, the upgrade skill's re-render step must also reinstall hooks, and the store-update command already does exactly that.
- **The advisory adds latency to session start** → One request with a short bounded timeout, cached per store for the configured interval, on a command that already waits on a network fetch from the remote. The timeout is the ceiling on the worst case, and it fails open.
- **Advisory text lands in agent transcripts** → It is once per session on stderr, not once per command, and it is suppressible by configuration for operators who do not want it. This is the specific cost that ruled out the ambient alternative.
- **Introducing network to `src/` invites the next feature to do the same** → The port is the mitigation: adding a second network call means either reusing the registry client, which is named for one job, or adding a second port and arguing for it in a design document. The requirement naming which commands must stay offline is the enforceable half.
- **A per-store cache re-fetches once per store per interval** → Accepted; see D6. The alternative costs a user-global state directory and a test surface that silently does nothing.
- **The skill could instruct an upgrade that does not affect the executable in use** → Precisely what D12's `linked` and `undetermined` classifications prevent, and the delta spec makes stopping on a linked working copy a requirement with its own scenario.

## Migration Plan

No migration. The configuration block is new and carries shipped defaults, so an existing `contexture.yaml` that omits it resolves through the defaults — the schema version is unchanged and no migration step is registered. Existing stores pick up the new and revised skills on their next `ctxr update`, through the shipped-skill sync that already refreshes every owned skill, and the harness bridge surfaces the new skill with no additional wiring.

Rollback is per-piece and clean: setting the configuration key false disables the advisory without removing anything, and reverting the change leaves no store-side state behind except one file under the derived-cache directory, which is gitignored, never read by anything else, and safe to delete.

The one ordering constraint during implementation is that the `version` command must exist and register its check option before the upgrade skill is rendered, because the existing check over rendered skills resolves the options a skill names against the CLI's own registration and will fail the build otherwise.
