# context-store Specification

## Purpose

Defines a context store as a git repository with one configuration file as its single source of truth, a note frontmatter schema, and the derived-vs-authored distinction that lets generated and human-written content coexist safely in the same files.

## Requirements

### Requirement: A context store is a git repository
`contexture init` SHALL create a git repository at the target root if one does not already exist, and every other contexture command SHALL refuse to operate on a root that is not inside a git repository, naming the missing repository as the reason.

#### Scenario: Init on a plain directory
- **WHEN** `contexture init` runs in an empty directory with no `.git`
- **THEN** the command creates a git repository, commits the initial store scaffold, and exits 0

#### Scenario: Command run against a non-git directory
- **WHEN** any contexture command other than `init` is run with `--root` pointing at a directory that is not inside a git repository
- **THEN** the command exits non-zero and reports that the root is not a git repository, without attempting any store operation

### Requirement: `contexture.yaml` is the single source of truth for store configuration
The store SHALL carry exactly one configuration file, `contexture.yaml`, at its root, and every contexture component SHALL read taxonomy (the set of top-level layers and their declared defaults), frontmatter field keys, and retrieval exclusion paths from this file rather than from a hardcoded value.

#### Scenario: Taxonomy is configured, not hardcoded
- **WHEN** `contexture.yaml` declares a set of top-level layers different from the shipped default profile
- **THEN** every command that enumerates or validates layers (placement, lint, doctor) operates against the configured set with no reference to the shipped default's layer names

#### Scenario: Exclusion paths come from config
- **WHEN** `contexture.yaml` lists a path prefix under retrieval exclusions
- **THEN** every retrieval leg (catalog, graph, content matching) treats notes under that prefix as non-retrievable, and no component maintains a second, independent exclusion list

### Requirement: The visibility field's frontmatter key is configurable with a shipped default
The store's visibility field key (the frontmatter key that names which context may see a note) SHALL be read from `contexture.yaml` (`fields.visibility`), with a shipped default value. No specification other than this one SHALL assert the literal key name; all other requirements SHALL refer to "the visibility field."

#### Scenario: Default key in a freshly initialized store
- **WHEN** `contexture init` runs with no `fields.visibility` override
- **THEN** the generated `contexture.yaml` records the shipped default key, and `contexture note resolve` reads that key from notes

#### Scenario: Renaming the visibility field key
- **WHEN** an operator changes `fields.visibility` in `contexture.yaml` and runs the corresponding migration
- **THEN** every note's frontmatter is rewritten to the new key and every command continues to resolve visibility correctly, with no other configuration or code change required

### Requirement: Note frontmatter schema
A note SHALL be a markdown file whose optional YAML frontmatter may declare, among configured fields: a title, a creation date, and the visibility field. A note with no frontmatter SHALL be treated as valid content; contexture SHALL NOT add frontmatter to an existing note without an explicit request to do so.

#### Scenario: Note with no frontmatter is valid
- **WHEN** `contexture lint` scans a note that has no YAML frontmatter block at all
- **THEN** the note is not reported as malformed; it is reported only under the visibility-fail-closed check defined in the context-visibility capability

#### Scenario: Frontmatter is not silently added
- **WHEN** a contexture write operation (e.g. `rollup write`, `archive`) modifies a note that has no frontmatter
- **THEN** the operation does not introduce a frontmatter block unless the operation's own contract (e.g. ingest, which the context-ingest capability defines) requires one

### Requirement: Derived files are declared and never committed
The store SHALL declare, in `contexture.yaml`, which files and paths are derived (regenerated by a contexture command rather than authored). `init` SHALL add every declared derived path to `.gitignore`, and no contexture write operation SHALL commit a derived path.

#### Scenario: A derived artifact is gitignored at init
- **WHEN** `contexture init` completes
- **THEN** the repository's `.gitignore` lists every path declared derived in `contexture.yaml`

#### Scenario: Rebuilding a derived artifact does not require a commit
- **WHEN** `contexture graph build` regenerates the graph artifact
- **THEN** the regenerated file is not staged, committed, or included in any session's diff

### Requirement: Marker-fenced generated regions
A single mechanism SHALL govern any region of an otherwise-authored file that a contexture command writes into: the region is delimited by a start and end marker; content outside the markers is preserved byte-for-byte; a write that finds a mismatched marker count (an unpaired start or end marker) SHALL abort having written zero bytes to the file, and SHALL exit non-zero naming the file and the mismatch.

#### Scenario: Regenerating a fenced region preserves the rest of the file
- **WHEN** a command that writes a fenced region (for example, a rollup) runs against a note whose fenced region already exists
- **THEN** all content outside the start and end markers is byte-identical before and after the write

#### Scenario: Mismatched markers abort with no partial write
- **WHEN** a note contains a start marker with no matching end marker
- **THEN** the write operation exits non-zero, names the file and the mismatch, and the file on disk is unchanged

### Requirement: Relocating a note preserves history
Any contexture operation that moves a note to a new path (for example, archiving) SHALL perform the move as a single tracked rename rather than deleting and recreating the file, so that version-control history for the note is preserved across the move.

#### Scenario: Archiving a note preserves its history
- **WHEN** `contexture archive <note>` relocates a note into an archive path
- **THEN** the underlying git operation is a rename, and `git log --follow` on the new path returns the note's full prior history

### Requirement: Tool-owned files default to one home directory
A newly initialized store SHALL place tool-owned files under a single hidden home directory at the store root: authored-but-tool-owned content (the catalog, identity files, procedure pack) in tracked subdirectories, and derived artifacts in a cache subdirectory that is the store's default declared derived path (and therefore gitignored by init's managed block). Every one of these locations SHALL remain individually configurable, and every component SHALL read the location from configuration — a store configured with other paths (including the previous root-level defaults) SHALL keep working without migration.

#### Scenario: A fresh init leaves the root uncontaminated
- **WHEN** `contexture init` runs in a directory
- **THEN** the catalog, identity files, and procedure pack are created under the home directory's tracked subdirectories, the derived cache subdirectory is the sole default gitignored derived path, and the only new root-level entries are the config file, the canonical entry document, and the home directory itself

#### Scenario: A store with legacy root-level paths keeps working
- **WHEN** a store's configuration declares root-level catalog/identity/procedure paths from before this change
- **THEN** every command reads and writes those configured locations unchanged, with no migration required

### Requirement: A line can be appended into a named fenced region
`ctxr entry append <note> --region <name>` SHALL insert the given text as a new line at the end of the note's `contexture:<name>` fenced region, creating the region at the end of the body when absent, and SHALL leave every byte outside the region — including frontmatter — unchanged. It SHALL report the region name and its resulting line count.

#### Scenario: Append into an existing region
- **WHEN** the note contains a `contexture:ledger` region with two lines and the command appends one
- **THEN** the region holds three lines, the reported count is 3, and the rest of the note is byte-identical

#### Scenario: The region is created when absent
- **WHEN** the note has no `contexture:ledger` region
- **THEN** the region is created at the end of the body containing the single appended line
